# AI Coding 可持续交付：Spec-Driven Development + Harness 梳理

---

## 一、核心观点：从"生成速度"到"交付确定性"

> Writing code is not the same as delivering.
> 在大规模工程中，AI Coding 必须服从团队的流程、约束、验证与学习闭环。

### 1.1 Vibe Coding 的四大问题

| 问题 | 具体表现 |
|---|---|
| 需求不完整 | 一句话需求，缺失上下文，AI 会把假设当结论 |
| 约束隐性化 | 模块边界、历史取舍很少被完整写下来 |
| 验证太晚 | 返工累积在 CR、测试、发布阶段 |
| 经验不沉淀 | 一次成功的交付不会自动改进下一次 |

### 1.2 核心结论

- **Vibe Coding** 提升的是 **生成速度**
- **大型项目** 需要的是 **交付确定性**
- 这是从"提示 AI"到"治理 AI 执行"的转变

---

## 二、SDD + Harness 是什么

SDD（Spec-Driven Development，规约驱动开发）+ Harness 是一种把 AI Coding 变成**受治理交付流程**的工程模式。

| 部分 | 作用 |
|---|---|
| **SDD** | 把需求、标准、反馈转化为可执行的规约：story、spec、plan 以及可复用上下文 |
| **Harness** | 把生成、验证、纠正变成带检查点和质量门禁的受控执行过程 |

> 行业信号：成熟的 AI Coding 正从"代码生成"转向"规约、约束、验证、知识留存"。

### 2.1 对比维度：Vibe Coding vs SDD + Harness

| 维度 | Regular Vibe Coding | SDD + Harness |
|---|---|---|
| 需求输入 | 自然语言一句话 | TAPD(Jira)、视觉稿、AI-Readiness |
| 上下文来源 | 本地文件 + 临时搜索 | iWiki(Conf)、模板、历史 |
| 任务表达 | 一次性生成 | tapd-raw → story → spec → plan |
| 运行时治理 | 依赖模型自主性 | 范围、检查点、护栏 |
| 结果验收 | 常靠"看起来对" | spec-diff、评审、CI、回测 |

> 核心观点：生成速度有用，但交付确定性需要治理。

---

## 三、SDD 第一步：在 AI 执行前对需求分层

> 不要把 TAPD(Jira) 直接丢给 AI 去写代码；要把证据、理解、工程表达分开，以供评审。

### 3.1 三层 SDD 产物栈

```
1. tapd-raw.md   保留证据
   TAPD(Jira) 原文 / 截图 / 目标 / 范围 / 上下文
        ↓
2. story.md      需求理解
   目标 / 非目标 / 规则 / 约束 / 流程
        ↓
3. spec.md / plan.md   工程表达
   What / Why / Scope / How / 验收 / 风险
```

### 3.2 团队收益

- **产品**：聚焦目标、范围、验收标准
- **工程**：聚焦范围、方案、计划
- **测试 / 评审**：聚焦风险、验收、验证路径
- **AI**：从清晰的规约出发，减少猜测

> 核心价值：不是多写文档，而是产出**可评审、可追溯、可复用**的工程输入。

---

## 四、SDD + Harness 如何进入研发流程

主工程流：

```
人 → 需求输入 → 规约(SDD) → 计划 → 实现(Harness) → 验证治理 → 合并与沉淀
     (TAPD(Jira) /       story/spec/plan   任务/范围/风险/验收  AI编码/本地工具/代码库  spec-diff/CR/PreCI/CI  MR/知识回写/基线更新
      产品上下文/验收)
```

### 4.1 SDD 入口（把上下文和经验变成规约）

1. **输入治理**：TAPD(Jira) 接入、视觉解析、AI-Readiness、澄清
2. **规约分层**：tapd-raw → story → spec → plan
3. **反馈留存**：vibe-done / 回测 / 知识回写 / 基线

### 4.2 Harness 入口（把生成放进工程护栏）

1. **执行边界**：worktree / 范围 / 检查点 / 用户决策
2. **验证门禁**：validate-spec / spec-diff-code / 本地测试
3. **组织级质量门禁**：AI 代码评审 / PreCI / MR / CI

### 4.3 外部系统与资产

- TAPD(Jira)：需求、验收标准
- iWiki(Conf)：知识库、标准、历史设计
- 代码仓库：架构边界、历史约束
- AI / 工具链：模型、技能、MCP、命令
- MR / CI：评审、检查、合并
- 知识资产：回测样本、基线、经验库

> 关键点：SDD 持续把需求和经验变成规约；Harness 让 AI 执行**受限、可验、可追溯**。

## 五、需求护栏：AI-Readiness 门禁

> AI-Readiness 尽早暴露模糊需求：够清楚就进入 SDD 分层，不清楚就先澄清。

### 5.1 流程

```
原始 TAPD(Jira) 输入
  ├─ 需求文本（如"增加导出按钮"）
  ├─ 截图/附件（页面状态、入口）
  └─ 验收描述（标准不完整）
        ↓ input screening
   AI-Readiness gate（就绪度评分，如 72 分）
     ├─ 目标清晰度
     ├─ 范围完整性
     ├─ 验收可验证性
     ├─ 约束覆盖度
     └─ 风险暴露度
        ↙        ↘
   通过 → 进入 SDD 分层    不通过 → 先澄清
   story→spec→plan       把缺口转成问题（目标/范围/验收/约束/风险）
```

> 核心要点：在编码前拦住模糊需求，把 AI 从"猜测"转向"确认后执行"。

---

## 六、需求澄清闭环：把 AI 的不确定显性化

> 当 AI-Readiness 发现缺口，生成可确认的问题，并把答案写回归约。

### 6.1 低就绪维度 → 按角色澄清 → 写回规约

| AI-Readiness 低分维度 | 对应角色澄清 | 写回的规约 |
|---|---|---|
| 目标不清（解决什么问题？） | **产品确认**：目标 / 非目标 / 范围 / 验收标准 | `story.md`：补充目标、非目标、业务边界 |
| 范围不清（哪些场景在/不在范围内？） | **工程确认**：技术边界 / 兼容性 / 影响 / 依赖 | `spec.md`：补充范围、工程约束、验收 |
| 验收不可验（什么算完成？） | **测试确认**：回归 / 边界情况 / 风险 / 发布验证 | `plan.md`：补充风险、验证路径、执行顺序 |
| 约束缺失（权限 / 配置 / 发布 / 回滚） | | |

澄清后重新检查，再进入 SDD 分层 / 执行。

> 核心结论：不要让 AI 猜，让它问出正确的问题，并把答案写进规约。

---

## 七、领域上下文装配：把团队规则带入 AI Coding

> 不要只把文档粘贴给 AI。要把 iWiki(Conf)、历史设计、规则模板、相似 MR 整合成规约约束。

### 7.1 上下文装配工作台

输入（需求 + 澄清结果 + AI-Readiness 结果）
→ **识别领域**
→ **领域 ID / 规则检索 / 约束整合 / 规约注入**
→ 注入到规约中

### 7.2 五大知识来源

| 来源 | 内容 |
|---|---|
| iWiki(Conf) | 业务规则、接口约定 |
| 历史设计 | 设计结论、坑 |
| 规则模板 | 权限 / 配置 / 发布 |
| 回测样本 | 漏点 / 基线 |
| 相似 MR | 真实变更路径 |

### 7.3 输出到三层规约

- `story.md`：业务规则、目标边界
- `spec.md`：工程边界、验收标准
- `plan.md`：风险、验证路径

> 核心要点：领域装配把团队规则变成规约约束，供生成、验证、评审共同使用。

## 八、执行边界：在 AI 修改代码前锁定范围

> AI 可以自主执行，但只能在清晰的目标、范围、文件、检查点之内。

### 8.1 双层护栏

- **上层护栏**：目标 / 非目标 / 验收 / 风险
- **下层护栏**：目标文件 / 模块边界 / 禁止区域 / 检查点

### 8.2 执行链路

```
spec.md / plan.md
  → Scope Lock（锁定目标与范围）
    → AI edits code（在边界内执行）
      → Checkpoint（方案 / 文件 / 测试 确认）
        → 可评审的变更（边界清晰、可解释）
```

### 8.3 护栏挡住的"跑偏风险"

- 越范围修改（Out-of-scope edits）
- 无关重构（unrelated refactoring）
- 兼容性破坏（compatibility breakage）
- 跳过确认（skipped confirmation）
- 把相关问题当成本次任务（treat related issues as this task）

> 核心结论：边界让 AI 自主权保持在团队可接受的范围内。

## 九、执行验证：用工程检查判断可交付性

> 生成的代码只是中间产物；要验证规约完整性、实现一致性、工程质量。

### 9.1 验证看板

**输入**：`spec.md / plan.md` + 代码 diff + 测试结果

三道关卡：

| 关卡 | 检查项 | 不通过的典型问题 |
|---|---|---|
| **spec completeness**（validate-spec） | 目标 / 范围 / 验收 / 风险 / 实现路径 | 字段缺失 |
| **implementation consistency**（spec-diff-code） | 漏点 / 设计漂移 / 越范围 / 无关修改 | 路径遗漏、越范围 |
| **engineering quality**（AI review / PreCI / CI） | 规范 / 测试 / CR / 主次修复 | 规范问题 |

不通过 → 问题清单 → AI 修复 / 人工确认 → 重新检查
通过 → **可评审的 MR**

> 核心结论：AI 不应自我证明；通过规约、评审、CI 来评估产出。

## 十、行业参考：Chromium AI Coding 政策

> AI 辅助不是责任外包。Chromium 的 AI Coding 政策是一个有力证据：成熟的 AI Coding 在强化人的问责。

### 10.1 责任要点（来自 chromium.googlesource.com）

1. **作者必须自查并理解所有代码和文档更新**（无论是否使用 AI 工具），确保正确性、设计、安全属性、风格符合项目标准。作者应能回答评审者的问题。
2. **Chromium 有严格的双提交者代码评审要求**；当作者是提交者时，他们算作两个人类评审者之一。**任何提交了本人不理解的 CL 的账号，都有失去提交者身份的风险**。再次违规可能被封禁。
3. **作者应标记出 AI 辅助但自己没把握的部分**，可在代码评审评论、CL 描述或代码注释中标明。
4. **作者必须声明提交的代码是其原创**，无论是否使用了 AI 工具。
5. **人类回复必须得到人类回复**：如果 AI 代理提交了 bug 或 CL，而人类给出了反馈，那么该代理的人类操作者必须亲自回复。

### 10.2 启示

- AI 可以辅助执行
- 但**理解、评审、交付责任**仍然由人承担

## 十一、知识回写：让一次交付改进下一次

> 交付不是终点；CR、测试、发布、回测经验必须成为下一次 AI 的上下文。

### 11.1 闭环流程

```
1. 交付完成（MR / CR / 测试 / 发布反馈）
        ↓
2. vibe-done 归档（新规则 / 路径 / 风险 / 评审反馈）
        ↓
3. 知识回写（iWiki(Conf) / 规则模板 / 基线 / 历史样本）
   → 持久化资产：iWiki 业务规则、Baseline 回测基线、规约资产模板/示例
        ↓
4. 下一次需求装配（领域检索 / 评分 / 规约生成 / 验证）
   → 回到团队知识资产（可检索 / 可复用 / 可验证）
```

### 11.2 不回写的代价

- CR 教训只停留在评论里
- 下一次 AI 又从零开始猜

> 核心结论：知识回写不是事后复盘，它把交付规则、风险、漏点变成下一次 AI 的上下文。

## 十二、回测（Backtest）：用真实 MR 对比 SDD + Harness 覆盖度

> 同一个历史需求：把真实交付与 SDD + Harness 重放做工程级一致性对比。

### 12.1 三栏对比

| 历史真实（ground truth） | SDD + Harness 重放 | 一致性评估 |
|---|---|---|
| 历史 TAPD(Jira)（原始需求 / 验收 / 评论） | SDD 生成的规约（story / spec / plan） | 规约覆盖度：覆盖了多少真实需求点？ |
| 真实 MR（工程师合并的改动） | Harness 约束下的执行（范围 / 检查点 / 代码草稿） | 文件覆盖度：覆盖了多少真实改动文件？ |
| 参考变更路径（文件 / 符号 / 配置 / 测试） | | 符号覆盖度：函数 / 枚举 / 配置 覆盖情况？ |

### 12.2 漏点分析与反馈优化

- 漏了 → 分析原因：是需求不清？知识缺失？模板缺失？还是护栏缺失？
- 反馈优化 → 规约模板 / iWiki(Conf) / 基线 / 护栏规则 → 改进下一次

## 十三、全流程总览：从需求治理到交付闭环

```
┌─────────────────────┐  ┌──────────────┐  ┌───────────────┐  ┌──────────────────┐  ┌──────────────┐
│ 需求输入治理         │  │ SDD 规约     │  │ Harness 护栏  │  │ 责任与评审        │  │ 反馈演进      │
│                     │  │              │  │               │  │                  │  │              │
│ TAPD(Jira) 原始需求  │→ │ tapd-raw.md  │→ │ 执行边界       │→ │ Chromium 政策证据 │→ │ 知识回写      │
│ AI-Readiness gate   │  │ story.md     │  │ Checkpoint    │  │ 人类作者承担责任  │  │ 团队资产      │
│ 需求澄清             │  │ spec.md      │  │ 执行验证       │  │ MR / CL 评审     │  │ 回测          │
│ 领域上下文装配       │  │ plan.md      │  │ 问题修复       │  │                  │  │              │
└─────────────────────┘  └──────────────┘  └───────────────┘  └──────────────────┘  └──────┬───────┘
            ↑                                                                                │
            └──────────────────────── feed next cycle ───────────────────────────────────────┘
```

### 13.1 最终目标

> 把 AI 从"代码生成"推进到一个**可评审、可验证、可留存、可问责**的工程过程中。

### 13.2 三大组成

| 组成 | 职责 |
|---|---|
| **SDD** | 把需求、澄清、领域上下文转成规约 |
| **Harness** | 为执行、验证、责任、反馈提供护栏 |
| **闭环** | 知识回写 + 回测，持续改进下一轮 |

## 十五、结语

> SDD + Harness 是当前 AI Coding 的趋势，但技术和方法会持续演进。随着模型、工具、平台、协作方式的进步，新的工作流会不断涌现。
