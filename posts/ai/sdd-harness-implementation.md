# SDD + Harness 落地执行方案

> 来源依据：`AI_Coding_SDD_Harness_梳理.md`
> 目标：把 SDD（规约驱动开发）+ Harness（执行护栏）从方法论变成团队可执行的日常流程

---

## 一、落地总策略：三阶段推进

```
Phase 1  最小闭环（2-3 周）    跑通 1 条需求的 SDD 全链路
Phase 2  团队标配（4-6 周）    形成模板/工具/评审机制，覆盖 80% 需求
Phase 3  持续进化（长期）       知识回写 + 回测 + 组织级质量门禁
```

**原则**：先跑通再优化，先人工再自动化，先试点再推广。

---

## 二、Phase 1：最小闭环（2–3 周）

> 目标：用 1–2 个真实需求，完整走通 "需求 → 规约 → AI 编码 → 验证 → 合并" 流程

### 2.1 准备工作（第 1 天）

| 事项 | 负责人 | 产出 |
|---|---|---|
| 选定 1–2 个试点需求（中等复杂度、有明确验收） | 产品 + 技术负责人 | 试点需求清单 |
| 确定试点团队（3–5 人：产品/后端/测试各 1） | 技术负责人 | 试点小组 |
| 对齐 SDD 三层产物的基本格式 | 全员 | 模板 v0.1 |
| 选定 AI 编码工具（Claude Code / CodeBuddy / Cursor 等） | 技术负责人 | 工具确定 |

### 2.2 三层规约模板（直接可用）

在项目根目录建 `docs/sdd/` 文件夹，每个需求一个子目录：

```
docs/sdd/
  └─ <需求编号>-<简称>/
       ├─ 01-tapd-raw.md      # 原始证据层
       ├─ 02-story.md         # 需求理解层
       ├─ 03-spec.md          # 工程规约层
       └─ 04-plan.md          # 执行计划层
```

### 2.3 AI-Readiness 评估表（手工版）

在写 story 之前，先做就绪度打分（每项 0–20 分，总分 100）：

| 维度 | 评分标准 | 得分 |
|---|---|---|
| 目标清晰度 | 是否明确"解决什么问题、为谁解决" | /20 |
| 范围完整性 | In / Out of Scope 是否清楚 | /20 |
| 验收可验证性 | 验收标准是否具体、可量化 | /20 |
| 约束覆盖度 | 技术/时间/合规约束是否列全 | /20 |
| 风险暴露度 | 主要风险是否已识别 | /20 |
| **总分** | | **/100** |

**规则**：
- ≥ 70 分 → 直接进入 SDD 分层
- 50–69 分 → 先澄清低分项再开始
- < 50 分 → 退回需求方补充

### 2.4 执行步骤（单条需求）

1. **需求录入**：填 `01-tapd-raw.md`（15 分钟）
2. **AI-Readiness 评估**：打分，决定是否需要澄清（10 分钟）
3. **需求澄清**：把低分项转成问题，找对应角色确认（1 天内异步完成）
4. **写 story.md**：产品或技术负责人输出需求理解（30 分钟）
5. **写 spec.md**：开发输出工程规约（1–2 小时）
6. **写 plan.md**：开发输出执行计划与验证路径（30 分钟）
7. **规约评审**：产品 + 开发 + 测试一起过一遍 spec（30 分钟会议）
8. **AI 编码**：把 spec + plan 丢给 AI，在范围内执行（2–4 小时）
9. **验证对照**：逐条核对 AC，跑测试，做 spec-diff（1 小时）
10. **人工 CR + 合并**：常规代码评审（按团队节奏）

### 2.5 Phase 1 验收标志

- ✅ 至少 1 条需求完整走完全流程
- ✅ 三层规约模板经过一次实际使用和修订
- ✅ 团队对"什么是好的 spec"有共同认知
- ✅ 产出 1 份复盘记录（哪些地方顺、哪些卡住）

## 三、Phase 2：团队标配（4–6 周）

> 目标：把 SDD 变成团队默认工作方式，配套工具和评审机制

### 3.1 模板固化与知识库

- [ ] 把 Phase 1 迭代后的模板放入团队文档库（iWiki/Confluence/飞书文档）
- [ ] 建立 **规约示例库**：把做得好的 3–5 份 spec 作为范例
- [ ] 建立 **常见坑清单**：从 Phase 1 的失败/返工中提炼，加入 spec 模板的风险章节

### 3.2 建立规约评审机制

| 评审类型 | 触发条件 | 参与者 | 时长 |
|---|---|---|---|
| **快速评审** | 常规需求 | 开发 + 测试（异步评论） | 30 分钟内 |
| **正式评审会** | 复杂需求 / 跨模块 / 高风险 | 产品 + 开发 + 测试 + 架构 | 1 小时 |
| **免评审** | 极小改动（≤1 文件，≤20 行） | 开发自查 | — |

**评审 checklist**：
- [ ] 目标是否清晰
- [ ] 非目标是否明确
- [ ] 验收标准是否可验证
- [ ] 改动范围是否列全
- [ ] 风险是否已识别并有对策

### 3.3 Harness 护栏落地（从轻到重）

#### 第 1 级：人工护栏（立即能用）

- **Scope Lock**：AI 开始写代码前，在 spec 里明确列出"要改的文件清单"和"禁止改动的文件"
- **Checkpoint**：AI 每完成一个步骤，先停下来等人确认，再继续下一步
- **禁止自动提交**：AI 生成的代码必须人工 review 后才能提交

#### 第 2 级：工具化护栏（2–4 周内落地）

| 护栏 | 实现方式 | 工具/命令 |
|---|---|---|
| 工作区隔离 | 用独立 worktree / 分支做 AI 编码 | `git worktree add` / Claude Code worktree 模式 |
| 范围检查 | 比对改动文件 vs spec 中列出的文件 | 脚本 / git diff --name-only |
| 规范检查 | 接入 lint / format / 静态检查 | eslint / pylint / 项目已有 CI |
| 测试门禁 | AI 编码后必须跑通相关测试 | `pytest` / `jest` 等 |
| spec-diff 检查 | 用 AI 对照 spec 检查代码实现 | 自定义 prompt / 脚本 |

#### 第 3 级：CI 级护栏（后续）

- [ ] PreCI：MR 创建时自动跑范围检查 + 规范检查
- [ ] AI 代码评审机器人：自动标注"此 MR 由 AI 辅助生成，请重点关注 xxx"

### 3.4 角色与职责调整

| 角色 | 变化 | 新增职责 |
|---|---|---|
| **产品** | 从"写需求"到"写 story + 确认验收" | 维护 story.md，确认非目标和验收标准 |
| **开发（作者）** | 从"写代码"到"写 spec + 指导 AI + 审查结果" | 写 spec/plan、给 AI 喂上下文、自查 AI 产出 |
| **开发（评审者）** | 多了一层"spec 评审" | 在编码前评审 spec，编码后评审代码 |
| **测试** | 从"事后测"到"事前参与验收定义" | 参与 spec 评审，检查 AC 是否可测 |

### 3.5 Phase 2 验收标志

- ✅ 团队 80% 以上的需求走 SDD 流程
- ✅ 有可用的 spec 模板和示例库
- ✅ 至少实现 3 项工具化护栏
- ✅ AI 产出的返工率（CR 打回次数）有可量化的下降趋势

## 四、Phase 3：持续进化（长期）

### 4.1 知识回写机制

每次需求交付后（合并后 3 天内），做一次轻量回写：

| 回写内容 | 写入位置 | 负责人 |
|---|---|---|
| 新业务规则 / 接口约定 | iWiki / 团队知识库 | 产品 + 开发 |
| 新的坑 / 反模式 | 「常见坑清单」文档 | 开发 |
| 规约模板优化建议 | spec 模板库 | 技术负责人 |
| 可复用的 AI prompt / 配置 | 项目 `.claude/` 或 `docs/ai-prompts/` | 开发 |

**轻量回写模板**：

```markdown
# 回写：<需求编号>

## 本次新增的业务规则
-

## 踩过的坑
- 现象：
- 原因：
- 对策：

## 对模板/工具的改进建议
-

## 可复用的 AI 配置 / prompt
-
```

### 4.2 回测（Backtest）机制

每季度选 3–5 个历史需求做回测：

1. 取历史 TAPD/Jira 原文 + 真实 MR 作为 ground truth
2. 用当前的 SDD+Harness 流程重放
3. 对比三项覆盖度：
   - **规约覆盖度**：AI 生成的 spec 覆盖了多少真实需求点？
   - **文件覆盖度**：AI 改的文件和真实改动文件重合度？
   - **符号覆盖度**：函数/类/配置的覆盖情况？
4. 分析漏点 → 反哺模板 / 知识库 / 护栏规则

### 4.3 组织级质量门禁

- [ ] AI 辅助生成的代码必须在 MR 描述中标记
- [ ] 高风险模块（核心交易、支付、权限）的 AI 改动需要双人 review
- [ ] 建立 AI 编码质量指标看板（覆盖率、返工率、缺陷率）

## 五、工具清单与推荐配置

### 5.1 必备工具

| 用途 | 推荐工具 | 说明 |
|---|---|---|
| AI 编码 | Claude Code / CodeBuddy / Cursor | 支持 context / worktree / 多代理优先 |
| 规约协作 | iWiki / Confluence / 飞书文档 / Markdown + Git | 选团队已有的 |
| 需求管理 | TAPD / Jira | 已有 |
| 代码评审 | 公司已有 MR/CR 工具 | 加一条 "AI 辅助" 标签 |
| 工作区隔离 | git worktree | 免费、零成本 |

### 5.2 推荐的项目目录结构

```
<项目根>/
  ├─ docs/
  │   └─ sdd/                     # SDD 规约文档
  │        └─ <需求编号>-<简称>/
  │             ├─ 01-tapd-raw.md
  │             ├─ 02-story.md
  │             ├─ 03-spec.md
  │             └─ 04-plan.md
  ├─ .claude/                      # Claude Code 配置（如用 Claude）
  │   ├─ project.md                # 项目说明，喂给 AI
  │   ├─ settings.json
  │   └─ skills/                   # 自定义技能
  ├─ scripts/
  │   ├─ check-scope.sh            # 范围检查脚本
  │   └─ spec-diff.sh              # spec-vs-code 对比脚本
  └─ tests/                        # 已有测试
```

| 时间 | 内容 | 产出 |

## 七、常见阻力与应对

| 阻力 | 原因 | 应对 |
|---|---|---|
| "写 spec 太慢了" | 初期不熟练，感觉比直接写代码慢 | 试点选中等需求；对比"写 spec 1 小时 vs 返工 3 天"的时间账 |
| "AI 自己能理解，不用写这么细" | 高估 AI 对业务上下文的理解 | 用 1–2 次"AI 猜错导致返工"的真实案例说话 |
| "产品不想写 story" | 觉得是额外工作 | 开发先帮写第一版，产品只做确认 + 改非目标 |
| "工具太复杂" | 自动化一步到位反而用不起来 | Phase 1 全手工，Phase 2 再逐步工具化 |
| "老需求怎么办" | 历史需求没有 spec | 不追溯；新需求新办法，老需求照旧 |

---

## 八、成功衡量指标

| 指标 | 定义 | 目标方向 |
|---|---|---|
| **spec 覆盖率** | 走 SDD 流程的需求 / 总需求 | Phase 2 达到 80% |
| **AI 编码返工率** | CR 打回 ≥2 次的 AI MR 占比 | 持续下降 |
| **需求澄清次数** | 编码阶段还要找产品确认的次数 | 持续下降 |
| **线上缺陷率** | AI 编码产出的需求线上缺陷数 | 不高于人工编码 |
| **知识回写数** | 每月回写的规则/坑/模板数 | 稳步增长 |

## 附：角色速查卡

### 产品经理
- ✅ 提供清晰的目标、非目标、验收标准
- ✅ 参与 story.md 确认
- ❌ 不需要写技术 spec

### 开发工程师（作者）
- ✅ 写 spec.md / plan.md
- ✅ 给 AI 喂上下文、设定范围
- ✅ 自查 AI 产出，确保自己完全理解
- ✅ 标记 AI 辅助的部分

### 开发工程师（评审者）
- ✅ 编码前评审 spec
- ✅ 编码后评审代码，重点关注设计和边界
- ❌ 不需要逐行读 AI 生成的代码

### 测试工程师
- ✅ 参与 spec 评审，检查 AC 是否可测
- ✅ 基于 spec 写测试用例
- ✅ 验证 AI 产出是否满足 AC
